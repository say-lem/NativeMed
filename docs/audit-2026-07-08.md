# Backend Audit — 2026-07-08

Full pass over `src/` (65 files, 5 modules: auth, cases/content, courses/enrollments,
payments/subscriptions, shared infra) looking for edge cases, race conditions, and quiet
failure modes rather than style. Items marked **[verified]** were independently re-read
against the live source after the initial pass; unmarked items reflect a single
read-through and are worth a second look before acting on them.

Summary: **4 critical, 7 high, 8 medium, 7 low.**

---

## Critical — money and access can silently drift from reality

### 1. Refunds are never handled
`src/modules/payments/service/payments.service.ts:79-98`

The webhook switch has no case for `charge.refunded`; it falls to `default: break`.
`Payment.status` even has a `'refunded'` enum value that's never written anywhere.

**Scenario:** an admin refunds a customer in the Stripe dashboard — the payment row stays
`succeeded` forever, `getTotalRevenue` keeps counting it, and the user keeps full access
unless the subscription is separately cancelled. **[verified]**

### 2. Every new subscription is recorded as two payments, not one
`src/modules/payments/service/payments.service.ts:137-178`

Stripe fires both `checkout.session.completed` and `invoice.payment_succeeded` for the
same first charge. One upserts on `stripeCheckoutSessionId`, the other on
`stripeInvoiceId` — different natural keys, so they never dedupe against each other.

**Scenario:** a user's first £24.99 payment produces two `succeeded` rows: revenue and
the user's own payment history both read 2x the real amount. **[verified]**

### 3. A late webhook can silently reactivate a cancelled subscription
`src/modules/subscriptions/service/subscriptions.service.ts:196-220`

`updateFromStripeSubscription` and `expireByStripeId` both do a blind
`findOneAndUpdate` by subscription ID with no check against event timestamp or current
status. Stripe doesn't guarantee delivery order.

**Scenario:** `customer.subscription.deleted` lands first (status → cancelled), then a
delayed, older `customer.subscription.updated` arrives after — it overwrites status back
to active and re-grants access to a subscription the customer already cancelled. **[verified]**

### 4. No reconciliation path if a webhook is ever lost
`src/modules/payments/` + `src/modules/subscriptions/` (whole)

All access state is purely webhook-driven — no polling job cross-checks the DB against
the Stripe API. Stripe retries a failing endpoint for up to ~3 days, then stops.

**Scenario:** a prolonged outage or misconfigured endpoint during that window means a
subscription Stripe already cancelled can stay `active` in the DB indefinitely, with
nothing to self-heal it.

## High — lockout, orphaned data, and requests that shouldn't fail

### 5. `updateUserByAdmin` can deactivate any admin, including the last one
`src/modules/auth/service/auth.service.ts:327-337`

`toggleUserStatus` explicitly blocks deactivating an admin account. `updateUserByAdmin`
is a separate, unguarded path to the same field — its schema (`auth.schema.ts:103`)
permits `isActive`, and the service does a raw `findByIdAndUpdate` with no role check.

**Scenario:** `PATCH /admin/users/:id { "isActive": false }` against any admin ID
(including the caller's own, or the only remaining admin) succeeds, and unlike the
guarded path it never purges that admin's refresh tokens either. **[verified]**

### 6. Deleting a course orphans every active enrollment in it
`src/modules/courses/service/courses.service.ts:90-93`

`deleteCourse` is a bare `findByIdAndDelete` — no check for and no cascade to existing
`Enrollment` docs.

**Scenario:** a course with paying enrolled users gets deleted; `GET /enrollments/me`
now returns those users a record with `courseId: null` after populate. Access can never
be cleanly revoked or restored against a real course again. **[verified]**

### 7. Login response leaks whether an account exists
`src/modules/auth/service/auth.service.ts:128-143`

The deactivated-account check runs *before* password verification and returns a
distinct 403 ("Your account has been deactivated") instead of the generic
invalid-credentials message — and the "no such user" branch returns instantly while the
wrong-password branch first runs a ~100ms bcrypt compare.

**Scenario:** either signal lets an attacker confirm a target email is a real, disabled
account without ever knowing the password. **[verified]**

### 8. No per-account brute-force protection on login
`src/app.ts` + `src/modules/auth/service/auth.service.ts`

The only defense is a shared, IP-keyed rate limiter (20 req / 15 min) across the entire
`/auth` prefix — there's no failed-attempt counter or lockout field on the user model.

**Scenario:** an attacker spreading attempts across IPs, or pacing ~1 request per 45
seconds from one IP, can brute-force a single account's password indefinitely.

### 9. `duplicateCase` can assign the same station number to two cases
`src/modules/cases/service/cases.service.ts:415-444`

`findOne().sort({stationNumber:-1})` then `+1` is read-then-write with no lock, and
`stationNumber` has an index but no uniqueness constraint.

**Scenario:** two admins duplicating a case around the same moment (or one admin
double-clicking) both read the same current max before either write lands — both new
cases silently get the identical station number.

### 10. The global 10KB body limit rejects real case-creation payloads — and fails ugly
`src/app.ts:65` + `src/shared/middleware/errorHandler.ts:50-58`

`express.json({ limit: '10kb' })` applies globally; nothing in `createCaseSchema` caps
section lengths. Serializing the actual seed data confirms 29 of 247 real cases (~12%)
exceed 10KB, up to 14.5KB. Worse, the resulting `PayloadTooLargeError` carries its own
413 status that `errorHandler.ts` doesn't check for, so it falls through to a generic
500 "Something went wrong" instead of an actionable error.

**Scenario:** an admin creating/editing a case with a normal-length marking scheme gets
a confusing server error instead of a clear "payload too large." **[verified]**

### 11. A post-connect Mongo error with no listener crashes the whole process
`src/config/db.ts:14-16`

Only `mongoose.connection.on('disconnected', ...)` is registered — there's no
`.on('error', ...)`. `mongoose.connection` is a plain Node `EventEmitter`.

**Scenario:** if it ever emits `'error'` after the initial connect (an auth or topology
error mid-session) with zero listeners attached, Node throws synchronously and takes the
entire server down, unlike the initial-connect failure which is caught cleanly. **[verified]**

## Medium — copy-paste drift, unenforced flags, missing bounds

### 12. `mustChangePassword` is stored but never enforced
`src/shared/middleware/authenticate.ts` + `src/modules/auth/service/auth.service.ts:306`

The flag is set on admin creation and returned in the login response, but no middleware
anywhere checks it.

**Scenario:** an admin created with an emailed temporary password can just never call
`/change-password` and keep using that password indefinitely with full admin access —
the flag is a UI hint only. **[verified]**

### 13. Password-reset tokens can be consumed twice under a race
`src/modules/auth/service/auth.service.ts:211-227`

`resetPassword` does `findOne({tokenHash, used:false})`, then separately sets
`used = true` and calls `.save()` — not an atomic `findOneAndUpdate`.

**Scenario:** two concurrent requests with the same raw token can both pass the
`used:false` read before either write commits, letting both proceed.

### 14. A failed content upload leaks a Cloudinary asset with zero logging
`src/modules/content/service/content.service.ts:41-65`

`uploadPdf` uploads to Cloudinary first, then creates the DB row. If
`CourseContent.create()` throws after the upload succeeds, the PDF is orphaned in cloud
storage — and unlike every comparable path in the cases module, there's no `try/catch`
or `console.error` here, so the leak is invisible.

### 15. Content deletion can get permanently stuck; the equivalent case path can't
`src/modules/content/service/content.service.ts:112-121`

`deleteCase` wraps its Cloudinary destroy call in `.catch()`, so the DB row is always
removed even if cloud storage errors. Content's `deleteContent` has no such guard.

**Scenario:** if `cloudinary.uploader.destroy` throws, `content.deleteOne()` never runs,
leaving that item permanently undeletable through the API.

### 16. The "falls back to regex search" comment describes code that doesn't exist
`src/modules/cases/service/cases.service.ts:23-27`

The comment claims a regex fallback if the text index isn't built yet; the code
unconditionally sets `filter.$text = {$search: ...}`.

**Scenario:** if the `cases_text_search` index is ever missing or mid-build on a large
collection, every search request throws "text index required for $text query" and 500s,
with no actual fallback.

### 17. Enrollment admin pagination has no upper bound
`src/modules/enrollments/controller/enrollments.controller.ts:32-48`

A zod schema capping `limit` at 100 exists in `enrollments.schema.ts` but is never
imported into the route. The controller instead does raw
`Number(req.query.limit) || 20` straight into Mongoose `.skip()/.limit()`, with no
ceiling.

**Scenario:** `?limit=5000000` goes straight through — unbounded query, inconsistent
with courses' validated pagination.

### 18. Re-subscribing after cancellation overwrites the old subscription's history
`src/modules/subscriptions/service/subscriptions.service.ts:180-194`

`upsertFromStripe` matches an existing case-bank subscription by `{userId, type}` only,
ignoring status.

**Scenario:** a new Stripe subscription after a prior cancellation reuses and overwrites
that same document, losing the earlier `stripeSubscriptionId` and cancellation record —
not an access bug, but it muddies any billing/audit trail.

### 19. Several routes skip ObjectId format validation that sibling routes have
`src/modules/content/routes/content.route.ts`, several routes in
`src/modules/courses/routes/courses.routes.ts`, and the restore route in
`src/modules/enrollments/routes/enrollments.routes.ts`

Cases routes validate every `:id` param before it reaches Mongoose. Content routes
validate none; course mutation routes (`PATCH /:id`, `DELETE /:id`, publish, thumbnail)
and the enrollments restore route do the same.

**Scenario:** a malformed ID hits `findById` directly and throws a Mongoose `CastError`,
most likely surfacing as a raw 500 instead of a clean 400.

## Low — smaller gaps, worth a pass but not urgent

### 20. `POST /logout` has no body validation
`src/modules/auth/routes/auth.route.ts:31`

Every other auth route runs through `validate(schema)`; logout doesn't.

**Scenario:** an empty or missing body reaches
`crypto.createHash('sha256').update(raw)` with `raw` undefined, throwing a `TypeError`
that surfaces as an unhandled 500 rather than a clean 400. **[verified]**

### 21. A deactivated user's existing access token still works until it expires
`src/shared/middleware/authenticate.ts:30-37`

`authenticate` only checks the JWT signature and expiry, never re-checking `isActive`
against the DB. `toggleUserStatus` purges refresh tokens on deactivation, but an
already-issued access token keeps working for its full 15-minute lifetime regardless.
Minor given the short TTL, but deactivation isn't instant. **[verified]**

### 22. List sorts have no tiebreaker on same-timestamp inserts
`src/modules/courses/service/courses.service.ts:118`,
`src/modules/enrollments/service/enrollments.service.ts:288,305,317`

Admin lists sort by `createdAt` alone, with no secondary key like `_id`.

**Scenario:** rows created in the same millisecond (a bulk seed, a batch admin action)
can be ordered inconsistently across page fetches, silently skipping or duplicating a
row at the page boundary.

### 23. Stripe webhook retries and real customer traffic share one rate-limit bucket
`src/app.ts:48,62,85`

`paymentsLimiter` is a single 80-req/15-min instance mounted on both the public webhook
route and the authenticated payments API. `express-rate-limit` keys by IP.

**Scenario:** a burst of Stripe retries from a shared egress point could throttle a real
customer's checkout call, or vice versa.

### 24. A missing env var still fails with a bare zod dump and no pointer to fix it
`src/config/env.ts:53-61`

Hit firsthand this session: a completely empty set of `STRIPE_*` vars produced a wall of
"expected string, received undefined" lines and nothing telling the operator to check
`.env.example`. The failure is correct, just not self-diagnosing. **[verified]**

### 25. `.env.example` omits the seed-script variables
`.env.example` + `src/scripts/seed-admin.ts:27-30`

`SEED_ADMIN_NAME/EMAIL/PHONE/PASSWORD` are read directly via `process.env` in
`seed-admin.ts` but never listed in `.env.example`. Low impact only because the script
itself prints the exact missing variable names when run.

### 26. A failed image upload during case creation leaves an orphaned draft
`src/modules/cases/service/cases.service.ts:182-198`

`MockCase.create()` runs before the image upload step.

**Scenario:** if the upload throws, the client sees a 500 but the draft case row
already exists. A naive retry then creates a second duplicate draft instead of fixing
the first — not harmful since it's an unpublished draft, but it accumulates orphaned
rows over time.

## Checked and ruled out

- Stripe webhook signature verification is correctly wired: `express.raw()` is scoped to
  the exact webhook path and registered before the global JSON parser, so
  `constructEvent` gets the untouched raw body. No dev-mode bypass exists.
- Currency amounts stay in minor units (pence) consistently across plans, payment
  records, and Stripe's own fields — no double-conversion found.
- Password hashes are never leaked: `select:false` plus a `toJSON` transform strip them
  from every response shape.
- Regex-injection in search filters is handled — `escapeRegex` is applied consistently
  on every path that embeds user input into a `$regex`.
- Duplicate-email registration races are safe: a unique index plus an `E11000` → 409
  mapping in the error handler cover it.
- Seed scripts are idempotent and exit cleanly — no CI hang risk.
